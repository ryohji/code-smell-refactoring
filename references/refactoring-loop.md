# フェーズ 3：1 項目ずつ修正する

## ループの構造

計画の 1 項目につき、次の 3 ステップを順に踏む。各ステップは別々の担当に任せる。ステップの境界でオーケストレーターに制御が戻るので、進捗を台帳に記録し、次に進むか止めるかを判断できる。

```
[A] 保護     テストがなければ追加する → グリーンを確認 → コミット
[B] 変更     小さなステップで書きかえる → 各ステップでグリーン維持 → コミット
[C] 検証     独立した目でグリーンとふるまい不変を確認する
```

**A と B を同じ担当に任せない。** テストを書いた本人が実装を変えると、自分の変更に合わせてテストを緩める誘惑が働く。保護と変更を分けることで、テストが独立した基準として機能する。

**C を省略しない。** B の担当は「グリーンになった」と報告するが、テスト件数が減っていたり（テストを消した）、skip が増えていたり（テストを無効化した）することがある。C は件数と skip 数を突きあわせる。

## ステップ A：テストで保護する

### すでにテストがある場合

担当に、対象関数を通るテストが実在するかを確認させる。「テストファイルがある」ことと「その関数がテストで保護されている」ことは別だ。カバレッジツールがあれば使う。ないなら、対象関数に一時的に例外を投げる行を入れてテストがレッドになるかを見る（確認後に必ず戻す）。この確認は数分で済み、「保護されているつもり」で壊す事故を防ぐ。

保護が薄い（呼ばれてはいるが assertion が弱い）場合は、下記の方法で足す。

### テストがない場合：実装に答えを教えてもらう

期待値を頭で計算しようとすると時間がかかり、しかも間違える。代わりにテストフレームワークに教えてもらう。

1. 空のテスト関数を追加してビルドを通す
2. 対象関数の呼びだしを追加してビルドを通す
3. 戻り値の期待値を**適当に決めて** assert する
4. テストを動かす。当然失敗する
5. **テストが表示した実際の値**で期待値を書きかえる
6. テストを動かす。成功する
7. テスト関数の名前を、成功した assertion の内容を表すように変更する

このやり方には既知のリスクがある。**実装のバグをそのまま「正しい値」として固定してしまう。**

だから担当には、記録した値が仕様として妥当かを併せて判断させ、疑わしいものに `SUSPICIOUS` の印をつけて報告させる。印がついた項目はテストにコメントを残し（`# TODO: 仕様確認 — 空入力で 0 を返すのは意図的か不明`）、フェーズ 4 でバグ候補として報告する。**ここでは直さない。** 目的は現状の保護であって、修正ではない。現状を固定しないと、あとで「壊したのか元からか」がわからなくなる。

### 良いテストの条件

- **assert はひとつ。** 失敗した assert 以降は実行されないので、複数あると原因の切り分けに何往復もかかる。
- **テスト名が assertion の説明になっている。** `test_color_of_lycoris_flower_is_red` のように、名前を読めば何を主張しているかわかる。名前が書けないなら、テストの目的が絞れていない。
- **条件分岐もループも書かない。** 分岐に入らない側は実行されないので無駄なうえ、読み手には「結局どちらが走ったのか」がわからない。引数で条件を確定させ、確実に生じる結果だけを assert する。
- **三角測量する。** 引数 1 つにつき最低 2 ケース。1 ケースだけだと「まぐれ当たり」で通ることがあり、読み手の手掛かりも少ない。1 引数なら 2 テスト、2 引数なら 4 テスト。
- **値の選び方。** まず期待するふるまいの代表値。次にエッジケース（ゼロ、1、マイナス 1、最大値、空、null）。既知のバグを再現する値があれば必ず入れる。
- **ゴールから書く。** `assert(???, 42)` → `assert(solve(???), 42)` → 引数を定義。この順で書くと、確かめたいことから逆算できて、余計な準備コードが混ざらない。
- **setup/teardown で条件を揃える。** xUnit は各テストを setUp/tearDown で挟むので、先行テストの成否によらず毎回同じ条件から始まる。

### 依存を切りはなす

ネットワーク・DB・ファイルシステム・シングルトン・時刻に依存する関数は、そのままではテストの再現性がない。切りはなし方は `dependency-breaking.md` を読む。

**モックの粒度は最小限に。** テストしたい振る舞いの再現を妨げているものだけを差しかえる。何でもモックすると、テストが「モックが正しく呼ばれたか」の確認になり、実装の変更に過敏に壊れる。

### A の完了条件

- 対象関数を通るテストが存在し、グリーンである
- 実装に一切手を入れていない（依存切りはなしのための最小限の変更は例外。その場合も**その変更だけで一度グリーンを確認しコミットする**）
- テスト件数が増えている（減っていない）
- コミット済み（`test: <対象>のテストを追加` など）

## ステップ B：小さなステップで書きかえる

### 原則

**1 コミット 1 変更、各コミットでグリーン。** レッドになったら、直そうとせず直前のコミットに戻す。「あと少しで直る」と思って進めると、複数の変更が絡んで原因が特定できなくなる。戻してやりなおすほうが速い。

**リファクタリングツールが使えるなら使う。** IDE の自動リネーム・自動抽出は機械的で安全なので、テスト保護なしでも実行できる。手で書きかえるのとは信頼性が段違いだ。

### 臭い別の手順

具体的な進め方は `patterns.md` に臭いごとにまとめてある。着手する項目の分類に対応する節だけを読む。全部読む必要はない。

代表例として、重複コードの整理はこう進む。

1. 重複を含むコードをテストで保護する（ステップ A で完了しているはず）
2. 重複部分のひとつを関数として抽出し、元の場所を呼びだしに置きかえる → テスト実行 → グリーン → コミット
3. 他の重複箇所を、抽出した関数の呼びだしに置きかえる → テスト実行 → グリーン → コミット（**箇所ごとに 1 コミット**）

### テストは変えない

リファクタリングの定義上、外部から見たふるまいは変わらないのだから、テストも変わらないはずだ。テストを直したくなったら、いま何が起きているかを確認する。

- **シグネチャを変えた** → ふるまいの変更ではない。呼びだし側の追随は必要。ただし、この場合も**テストの assertion（期待値）は変えない**。変わるのは呼びかただけ。
- **期待値を変えたくなった** → ふるまいを変えている。それはリファクタリングではない。実装を戻し、ユーザーに報告して仕様変更として扱う。
- **テストが邪魔なので消したい** → 非公開の補助関数のテストなら、その関数が消えるなら一緒に消してよい。公開関数のテストなら消さない。

なお、非公開関数のテストが実装改善の妨げになるのは既知の摩擦点だ。**非公開の補助関数が不要になったら、そのテストは潔く捨てる。** 公開関数のテストを優先し、そちらが守られているなら内部構造は自由に変えていい。

### B の完了条件

- 計画の 1 項目が完了している
- 全コミットでグリーンが保たれている
- テストの assertion を変更していない
- 差分の要約（何をどう変えたか）が 20 行以内でまとまっている

## ステップ C：検証する

A と B を担当していない第三の担当に、次を機械的に確認させる。

1. **テストがグリーンである。** フェーズ 0 で決めたコマンドをそのまま実行する。
2. **テスト件数が減っていない。** A の前後と B の後で件数を比較する。減っていれば、B がテストを消している。
3. **skip / xfail が増えていない。** グリーンに見せるための無効化を検出する。
4. **テストの assertion が変わっていない。** テストファイルの差分を見て、期待値が書きかえられていないかを確認する。呼びかたの変更（引数の増減、名前の変更）は許容。期待値の変更は違反。
5. **ふるまいを変える変更が混ざっていない。** 実装差分に、条件の追加・エラー処理の変更・デフォルト値の変更など、意味を変える変更がないか。
6. **テストが本当にこの変更を検証している。** 変更箇所を意図的に 1 つ壊し、レッドになることを確かめる（確認後は必ず戻す）。レッドにならなければ、それはテストの穴。詳細は `task-prompts.md` のステップ C の指示文を読む。
7. **報告に書かれた数値が事実である。** 下記「報告の数値を検証する」を読む。

違反があれば、**オーケストレーターは該当項目を差し戻す。** B をやりなおすか、その項目を棚上げにするかを判断する。3 回やりなおして通らない項目は棚上げにし、理由を記録する。粘るより、他の項目に時間を使ったほうが総合的な成果が大きい。

### 報告の数値を検証する

報告に書かれた**具体的な数値は、そのまま台帳に転記せず確かめる。** 「テスト 269 件」「失敗 47 件」「行数 71 行削減」のような数値は、あとから根拠として使われるので、誤りが残ると判断を誤らせる。

数値の誤りは悪意なく起きる。作業の途中で試した別の変更の結果を覚えていた、複数回の試行が混ざった、記憶で書いた、など。**再現できる数値は再現して確かめる。**

- **テスト件数** → 実行して数える
- **意図的な破壊で N 件レッド** → 同じ破壊を自分でやって数える
- **行数の変化** → `wc -l` で確かめる
- **カバーした入力の範囲** → 「全域で一致」と書かれていたら、その範囲が本当に全域か（型の範囲と照らす）

**数値が違っていても、結論が変わらなければ差し戻さない。** 記録を正しい値に直して先に進む。ただし「レッドになった」が「ならなかった」の誤りだった場合は結論が変わるので、その項目は差し戻す。

この確認が効くのは、**数値が次の判断の根拠になる**ときだ。「18 件レッド」か「47 件レッド」かは保護の強さの見積もりに関わる。「テストが 269 件ある」は、次の担当が「減っていないか」を判定する基準になる。誤った基準を渡すと、次の担当が誤りに気づけない。

## 進捗の記録

各項目が終わるたび、オーケストレーターは `REFACTORING_PLAN.md` の該当行の状態を更新する。会話ではなくファイルに書くのは、コンテキストが圧縮されても失われないからだ。

状態は `未着手` / `保護済み` / `修正済み` / `検証済み` / `差し戻し` / `棚上げ` のいずれか。

**3 項目ごとに、ユーザーへ短い中間報告を入れる。** 完了した項目、残り、想定外に出てきたこと。長時間黙って進めると、方針がずれていた場合の手戻りが大きくなる。

## 並行して進めてよいか

**同一ファイルを触る項目は並行させない。** 編集が衝突する。

異なるファイル・異なるモジュールの項目は並行できる。その場合も、テスト実行は共有資源なので、各担当に**テストを実行する前に他が実行中でないことを前提にしない**よう指示する。実務上は、修正は逐次に保ち、**フェーズ 1 の検出とフェーズ 4 の仕様起こしだけを並行させる**のが安全で、速度の損失もほとんどない。

# 依存の切りはなし

テストできない関数のほとんどは、切りはなせない依存を抱えている。ネットワーク、
DB、ファイルシステム、シングルトン、現在時刻、乱数、環境変数、静的初期化。
これらがあると実行結果が再現しないので、assert が書けない。

切りはなしの原理はひとつ。**呼びだす対象を、外から差しかえられるようにする。**
「型」（引数の型の組と戻り値の型）が同じものは入れかえ可能だから、同じ型を
持つ偽物を渡せばテストできる。

## どのパターンを選ぶか

**まず「本体を変えずに済むか」を検討する。** テストのないコードを保護するのが
目的なのに、保護のために本体を変えるのでは順序が逆になる。

| | 本体の変更 | 手段 |
|---|---|---|
| **C：外側からの差しかえ** | **不要** | 言語の差しかえ機構（リンク順、モジュール解決、特異メソッド） |
| **A：抽象の導入** | 必要 | インターフェース／プロトコル。設計として残す価値がある場合 |
| **B：引数化** | 必要 | 操作の組を引数で受けとる。関数ポインタ、コールバック、オブジェクト |
| **D：非決定性の除去** | 場合により | 時刻・乱数・環境変数。A/B/C と組みあわせる |

**順序は C → A/B。** C で足りるならそれで保護し、リファクタリング（ステップ B）
の段階で必要なら A・B の形に整える。**保護と設計改善を混ぜないほうが、どちらも
安全に進む。**

**C の具体的な手段は言語ごとに違う。** 使用言語の言語パックを読む
（`lang/c.md` のリンクシーム、`lang/dynamic.md` のモジュール差しかえ、
`lang/oo.md` のインターフェース差しこみ）。

## 手順の共通形（A・B の場合）

1. 対象が使っている、テストの妨げになっている操作を特定する
2. その操作と同じ「型」を持つ抽象（インターフェース、関数の組、コールバック）
   を定義する
3. 対象が、その抽象を経由して操作を呼ぶように変える。**本番の呼びだし側は、
   元の実体をラップしたものを渡す**
4. テストでは、都合のよい値を返す偽物を渡す

**3 番を単独でコミットする。** この時点でテストはまだ増えていないが、既存の
ふるまいは変わっていない。ここでグリーンを確認しておくと、次にテストを足した
ときに「通らないのは切りはなしのせいか、テストの書き方のせいか」を切り分け
られる。

**抽象には、対象が実際に呼んでいる操作だけを入れる。** 元の全操作を写すと、
偽物の実装が重くなってテストを書く気が失われる。

## パターン D：時刻・乱数・環境変数

再現性がない典型。同じ原理で、値を「取ってくる関数」を差しかえる。

- 現在時刻：`now()` を引数か注入可能な関数にする。テストでは固定値を返す
- 乱数：シードを引数にとるか、生成器そのものを注入する
- 環境変数：起動時に読んで設定オブジェクトに詰め、以後はそれを引数で渡す

**「テスト時だけ分岐する」実装にしない。** `if (isTest) return FIXED_TIME;` の
ような条件は、本番コードにテストの都合を持ちこんでいる。本番で誤って有効になる
危険があるうえ、テストしているコードと本番で走るコードが別物になる。

## モックの粒度

**テストしたいふるまいの再現を妨げているものだけを差しかえる。**

何でもモックすると、テストが「モックが期待通り呼ばれたか」の検証になる。それは
実装の内部構造をテストしているのであって、ふるまいをテストしていない。だから
内部を変えるたびにテストが壊れる。**リファクタリングを守るために書いたテストが、
リファクタリングの邪魔をする**という本末転倒が起きる。

- **差しかえる：** 外部 I/O、非決定性（時刻・乱数）、遅い処理、テスト環境で
  用意できないもの
- **差しかえない：** 純粋な計算、同一モジュール内の補助関数、値オブジェクト、
  単純なデータ構造

## 代役にしてはいけないもの

未解決の依存を**機械的に埋めていくと危険な代役が混ざる。** 「何が足りないか」は
ツールが教えてくれるが、「何を返すべきか」は自分で判断する必要がある。

**計算結果を返す純粋関数を「常に 0 を返す」代役にしてはいけない。** 例えば
`distance()` が常に 0 を返すと、次のような壊れ方をする。

- `while (distance(...) > dis)` が**ループの意味を失う**（一度も回らない）
- `cdis = distance(...)` が**「すべてが隣接している」状態を作る**
- テストが通っても、**その経路のふるまいが「正しい」と誤って固定される**

厄介なのは、**いまテストしていない経路でも害があること**だ。将来テストがそこに
及んだとき、代役が返す誤った値を期待値として記録してしまう。

| 対象 | 代役にしてよいか | 理由 |
|---|---|---|
| 画面出力、ログ、音 | **よい**（捨てる、または記録する） | 結果が計算に影響しない |
| 外部 I/O（ファイル、ネットワーク、DB） | **よい**（都合のよい値を返す） | テスト環境で用意できない |
| 乱数、時刻 | **よい**（固定値。引数と回数を記録する） | 再現性のため差しかえが目的 |
| **純粋な計算関数** | **いけない** | 本物を使うか、実装を写す |
| **判定・分岐に使う値を返す関数** | **いけない** | 呼びだし側の制御フローが変わる |
| 対象が依存する業務ロジック | **いけない** | 代役にするとテストの意味が消える |

### 本物を使えないときは写す

依存が芋づるで付いてくる場合、**実装を写す**。ただし写しは本体と乖離するので、
次の 2 つを必ずやる。

1. **写しであることをコメントで明記する。** どのファイルの何行目から写したか
2. **本物のふるまいを固定するテストを別に用意する。** 乖離したら気づける

写した直後に、**本物と文字単位で一致することを確認する**（両方を取りだして
差分をとる）。手で写すと転記ミスが入る。

### 代役の見直しは定期的に

代役は増えるほど「何を潰しているか」が見えにくくなる。**項目をいくつか終えたら、
代役の一覧を読みなおす。** 「常に 0 を返す」「常に false を返す」ものを探し、
それが呼びだし側の判定に使われていないかを確かめる。

## モックは「渡された引数」も記録する

**戻り値を固定するだけのモックは、保護に穴を作る。** 固定できるのは「返る値」
だけで、**呼びだし側が渡した引数が正しいかは検証できない。** `randint(16)` と
書くべきところを `randint(15)` に取りちがえても、返る値が同じならテストは通る。
配列の要素数を渡している場合、これは配列外アクセスの見逃しになる。

だから**引数と呼びだし回数を記録し、テストから読みとれるようにする**。読みとり
用の窓口（本体には存在しない関数）を代役の側に足す。記録は setUp で消す。

| 記録する対象 | 検出できる誤り |
|---|---|
| **引数の値** | 定数・添字・上限の取りちがえ |
| **呼びだし回数** | 乱数列のずれ。**回数が変わると以後の乱数がすべてずれる**ので、ゲームやシミュレーションでは目に見えないふるまいの変更になる |
| **呼びだし順序** | 副作用の順序が意味を持つ場合（ログ出力、状態遷移） |

**呼びだし回数の記録はとくに価値が高い。** 「同じ計算を 2 回するようになった」
ことは戻り値だけ見ていると気づけない。純粋関数なら結果は同じだが、乱数や時刻の
ように**呼ぶこと自体が状態を変える**関数ではふるまいが変わってしまう。

**ただしやりすぎない。** 記録するのはそのテストで検証したい性質に関わるものだけ。
判断の目安は**その引数が間違っていたら本番で壊れるか**。配列の上限、ファイルの
モード、タイムアウト値などが該当する。

## モックが返す値

**「ありそうな値」を返させる。** 実際の API が返さない値を返させたテストは、
通っても何も保証しない。

正常系のほか、外部依存の失敗系（接続エラー、タイムアウト、不正なレスポンス、
空のレスポンス）も返させる。外部依存の失敗は本番で必ず起きるが、モックなしでは
テストできない。**これはモック導入の最大の見返りだ。**

## 切りはなしのコストが見あわないとき

- **より外側でテストする。** 単体テストが書けないなら、その関数を含むより大きな
  単位でテストする。実 I/O を伴っても、保護がゼロよりはるかにマシだ。ただし
  遅いテストは実行されなくなるので、通常のテストと分けて実行できるようにする
- **テスト用の実体を用意する。** インメモリ DB、一時ディレクトリ、ローカルの
  テストサーバー。モックより手間はかからず、本物に近い
- **その項目を棚上げする。** 切りはなしコストが修正の価値を上回るなら、それは
  正当な判断だ。理由を記録してユーザーに報告する

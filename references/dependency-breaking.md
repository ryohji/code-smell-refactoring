# 依存の切りはなし

テストできない関数のほとんどは、切りはなせない依存を抱えている。ネットワーク、DB、ファイルシステム、シングルトン、現在時刻、乱数、環境変数、静的初期化。これらがあると実行結果が再現しないので、assert が書けない。

切りはなしの原理はひとつ。**呼びだす対象を、外から差しかえられるようにする。** 関数の「型」（引数の型の組と戻り値の型）が同じものは入れかえ可能だから、同じ型を持つ偽物を渡せばテストできる。

## どのパターンを選ぶか

**まず「本体を変えずに済むか」を検討する。** テストのないコードを保護するのが目的なのに、保護のために本体を変えるのでは順序が逆になる。本体を変えずに済むなら、それが最も安全だ。

| | 本体の変更 | 使える場面 |
|---|---|---|
| **C：リンクシーム＋フィクスチャ** | **不要** | C/C++ などリンク時解決のある言語。Python/JS のモジュール差しかえ機構も同類 |
| **A：インターフェース導入** | 必要 | オブジェクト指向言語。設計として残す価値がある場合 |
| **B：関数ポインター／引数追加** | 必要 | C 言語。API・シングルトンへの依存 |
| **D：時刻・乱数・環境変数** | 場合により | 非決定性の除去。A/B/C のいずれかと組みあわせる |

順序としては **C → A/B** を検討する。C で足りるならそれで保護し、リファクタリング（ステップ B）の段階で必要なら A・B の形に整える。**保護と設計改善を混ぜないほうが、どちらも安全に進む。**

## 手順の共通形（A・B の場合）

1. 対象関数が使っている、テストの妨げになっている操作を特定する
2. その操作と同じ「型」を持つ抽象（インターフェース、関数ポインター、構造体、コールバック）を定義する
3. 対象関数が、その抽象を経由して操作を呼ぶように変える。**本番の呼びだし側は、元の実体をラップしたものを渡す**
4. テストでは、都合のよい値を返す偽物（モック）を渡す

**3 番を単独でコミットする。** この時点でテストはまだ増えていないが、既存のふるまいは変わっていない。ここでグリーンを確認しておくと、次にテストを足したときに「テストが通らないのは切りはなしのせいか、テストの書き方のせいか」を切り分けられる。

## パターン A：インターフェースによる置きかえ（オブジェクト指向言語）

構築困難なオブジェクト（ネットワーク接続、DB コネクション、外部サービスのクライアント）を持つクラス。

**1. 現状**

```java
public class ApiProxy {
    private HttpConnection connection;   // 実際に通信してしまう
    public List<User> listUsers() {
        HttpResponse response = connection.get("/users", cookie);
        ...
    }
}
```

**2. 使っている操作だけのインターフェースを定義し、差しかえ口を開ける**

```java
public class ApiProxy {
    private IHttpConnection connection;
    public IHttpConnection replace(IHttpConnection connection) {
        IHttpConnection old = this.connection;
        this.connection = connection;
        return old;                       // 差しかえ前を返すと復元できる
    }
    ...
}
```

**3. モックを差しこんでテストする**

```java
public class TestApiProxy {
    @Test
    public void user_list_is_empty_when_server_returns_OK_without_body() {
        api.replace(new MockConnection() {
            public Response get(String endpoint, Cookie cookie) {
                return Response.OK;      // 空ボディ
            }
        });
        assertThat(api.listUsers(), is(new ArrayList<User>()));
    }
}
```

**4. 本番実装は元のオブジェクトをラップする**

```
IHttpConnection ←── HttpConnectionProxy ──has──> HttpConnection（本物）
       ↑
       └────────── MockConnection（テスト用）
```

`HttpConnectionProxy` は `HttpConnection` を保持して呼びだしを転送するだけの薄い層。ここにロジックを入れないこと。テストされない層になるので、薄く保つ。

**インターフェースには、対象が実際に呼んでいるメソッドだけを入れる。** 元のクラスの全メソッドを写すと、モックの実装が重くなってテストを書く気が失われる。

## パターン B：API・シングルトンの置きかえ（C 言語ほか）

グローバル関数（標準ライブラリ、OS API）やシングルトンへの依存。

**1. 現状**

```c
void* decrypt_file(void* secret, const char* path) {
    char header[32];
    FILE* fp = fopen(path, "rb");                       // 実ファイルが必要
    size_t n = fread(header, sizeof(header), 1, fp);
    ...
}
```

**2. 使っている API と同じ型を持つ関数ポインターの組を定義**

```c
struct file_op {
    FILE*  (*open)(const char*, const char*);
    size_t (*read)(void*, size_t, size_t, FILE*);
    int    (*close)(FILE*);
};
```

**3. 対象関数に、その組を引数で受けとらせる**

```c
void* decrypt_file(void* secret, const char* path, struct file_op file_op) {
    char header[32];
    FILE* fp = file_op.open(path, "rb");
    size_t n = file_op.read(header, sizeof(header), 1, fp);
    ...
}
```

**4. モックでテストする**

```c
TEST(decrypt_file, succeeds_decrypt_with_valid_header) {
    struct file_op mocked = { mock_open, mock_read, mock_close };
    ASSERT_STREQ((char*)decrypt_file(MockSecret, "test.enc", mocked), MockPlainText);
}
```

**引数を増やせない場合**（呼びだし元が多すぎる、公開 API である）は、次のいずれかを使う。

- **既存シグネチャを保つラッパーを残す。** `decrypt_file(secret, path)` は本物の `file_op` を渡して新しい関数を呼ぶだけにする。呼びだし元は一切変えなくてよい
- **差しかえ可能なグローバル変数にする。** `static struct file_op g_file_op = { fopen, fread, fclose };` を用意し、テストから差しかえる。**テストの teardown で必ず元に戻す。** 戻さないと後続のテストが汚染され、実行順によって結果が変わる最悪のテストになる

## パターン C：リンクシームとテスト用フィクスチャ（C / C++ / リンク時解決のある言語）

**本体のソースを一行も変えずにテストできる**、最も強力な手口。C 言語のように「リンク時にシンボルが解決される」言語では、テスト実行形式に何をリンクするかを選ぶだけで依存を差しかえられる。

パターン A・B は本体に手を入れる（インターフェース導入、引数追加）。それに対してこの手法は**本体を無変更のまま保護できる**ので、「テストのないコードは触らない」という原則との相性が最もよい。グローバル変数・シングルトン・巨大なデータテーブルに依存する関数が対象。

### 手順

1. **テスト対象の関数を含む `.o` だけをコンパイルする。** ファイル単位で切りだす
2. **リンクして、未解決シンボルの一覧を得る。** これが「対象が必要とするものすべて」の正確な一覧になる。推測せずコンパイラに教えてもらう
3. **未解決シンボルを 3 つに分類する**
   - **本物をリンクできるもの**（定数テーブル、純粋な計算関数）→ その `.o` を足す
   - **テスト用に用意すべきデータ**（グローバル変数、状態を持つ配列）→ フィクスチャモジュールに定義する
   - **代役で足りるもの**（画面出力、乱数、ファイル I/O）→ フィクスチャにスタブを書く
4. **フィクスチャモジュールに、テスト専用の初期化関数を足す**
5. リンクが通ったらテストを書く

### 未解決シンボルの一覧を得る

```bash
gcc -std=c17 -Isrc -c -o /tmp/desc.o src/desc.c
gcc -o /tmp/t test.c /tmp/desc.o 2>&1 \
  | grep 'undefined reference' | sed 's/.*undefined reference to //' | sort -u
```

**この一覧が設計の出発点。** 何をモックすべきかを頭で考える必要がない。リンカが漏れなく列挙してくれる。

### フィクスチャモジュールの中身

```c
/* tests/fixture.c -- テスト用のグローバルデータと初期化関数
 *
 * 本物のデータ（定数テーブル）は本体の .o をそのままリンクして使う。
 * ここに置くのは、本体では別ファイルに散っていて一緒にリンクできないものだけ。
 */
#include "types.h"

player_type py;        /* 本体では player.c（巨大データと同居していて切りだせない）*/

/* テスト専用。オリジナルには存在しない。
 * setUp から呼ぶことで、先行テストの影響を受けない条件を作る。 */
void fixture_reset(void)
{
    extern inven_type inventory[];
    memset(inventory, 0, sizeof(inven_type) * INVEN_ARRAY_SIZE);
    memset(&py, 0, sizeof py);
}

/* --- スタブ --- */
void msg_print(char *str) { (void)str; }   /* 画面出力は捨てる */

/* 乱数はテストから制御できるようにする */
static int fixture_randint_value = 1;
int randint(int maxval) { (void)maxval; return fixture_randint_value; }
void fixture_set_randint(int value) { fixture_randint_value = value; }
```

**要点は 4 つ。**

- **本物のデータテーブルは本物をリンクする。** 数百行の定数表を写すと、本体が変わったときに乖離する。リンクできるなら必ず本物を使う
- **フィクスチャは最小限に。** 本体と一緒にリンクできないものだけを定義する。重複定義（`multiple definition of ...`）が出たら、それは本物をリンクできるということなので、フィクスチャから消す
- **テスト専用の関数を足してよい。** `fixture_reset()` や `fixture_set_randint()` は本体に存在しない。テスト用モジュールの中にあるので、**本体の実装には一切影響しない**。これがこの手法の要点で、本体を汚さずにテスト環境を作れる
- **`fixture_reset()` は setUp から呼ぶ。** グローバル状態を使うテストは、前のテストの影響を受けると実行順で結果が変わる。xUnit は各テストを setUp で挟むので、ここで毎回まっさらに戻す

### 参照箇所をポインター経由に置きかえる小技

グローバル変数そのものを差しかえたい場合、**参照箇所をポインター経由にする**という手もある。

```c
/* 変更前：グローバルを直接参照 */
extern player_type py;
/* 変更後：ポインター経由。本番では本物を指し、テストでは別の実体を指せる */
extern player_type *py_ptr;
#define py (*py_ptr)
```

マクロで元の記法を保てば、**参照箇所（数百箇所ありうる）を書きかえずに済む**。ただしこれは本体への変更なので、パターン C 本来の「本体無変更」は崩れる。リンクシームで足りるならそちらを選ぶ。

### この手法が向く場面・向かない場面

**向く**：グローバル変数への依存が広い、シングルトン、巨大なデータテーブル、レガシーな C コード、本体を変えずに保護したい場合。

**向かない**：リンク時解決のない言語（Python、JavaScript のモジュールシステム）。それらの言語では、モジュールの差しかえ機構（`unittest.mock.patch`、`jest.mock`）が同じ役割を果たすので、そちらを使う。

**注意**：ヘッダに `static inline` で書かれた関数や、マクロで展開される処理はリンクシームで差しかえられない。プリプロセッサの段階で確定してしまうため。その場合はパターン A・B に戻る。

## パターン D：時刻・乱数・環境変数

再現性がない典型。同じ原理で、値を「取ってくる関数」を差しかえる。

- 現在時刻：`now()` を引数か注入可能な関数にする。テストでは固定値を返す
- 乱数：シードを引数にとるか、乱数生成器そのものを注入する
- 環境変数：起動時に読んで設定オブジェクトに詰め、以後はそれを引数で渡す

**「テスト時だけ分岐する」実装にしない。** `if (isTest) return FIXED_TIME;` のような条件は、本番コードにテストの都合を持ちこんでいる。本番で誤って有効になる危険があるうえ、テストしているコードと本番で走るコードが別物になる。

## モックの粒度

**テストしたいふるまいの再現を妨げているものだけを差しかえる。**

何でもモックすると、テストが「モックが期待通り呼ばれたか」の検証になる。それは実装の内部構造をテストしているのであって、ふるまいをテストしていない。だから内部を変えるたびにテストが壊れる。**リファクタリングを守るために書いたテストが、リファクタリングの邪魔をする**という本末転倒が起きる。

判断の目安。

- **差しかえる：** 外部 I/O、非決定性（時刻・乱数）、遅い処理、テスト環境で用意できないもの
- **差しかえない：** 純粋な計算、同一モジュール内の補助関数、値オブジェクト、単純なデータ構造

## 代役にしてはいけないもの

リンクシームで代役を並べるとき、**未解決シンボルを機械的に埋めていくと危険な代役が混ざる。** リンカは「シンボルが足りない」ことしか教えてくれないので、何を返すべきかは自分で判断する必要がある。

**計算結果を返す純粋関数を「常に 0 を返す」代役にしてはいけない。**

```c
/* 危険：呼びだし側の意味を壊す */
int distance(int y1, int x1, int y2, int x2) { return 0; }
```

これが混ざると次のような壊れ方をする。

- `while (distance(...) > dis) { ... }` が**ループの意味を失う**（常に偽なので一度も回らない）
- `m_ptr->cdis = distance(...)` が**「すべてが隣接している」状態を作る**
- テストが通っても、**その経路のふるまいは「正しい」と誤って固定される**

厄介なのは、**いまテストしていない経路でも害があること**だ。将来テストがそこに及んだとき、代役が返す誤った値を期待値として記録してしまう。

### 判断の基準

| 対象 | 代役にしてよいか | 理由 |
|---|---|---|
| 画面出力、ログ、音 | **よい**（捨てる、または記録する） | 結果が計算に影響しない |
| 外部 I/O（ファイル、ネットワーク、DB） | **よい**（都合のよい値を返す） | テスト環境で用意できない |
| 乱数、時刻 | **よい**（固定値。引数と回数を記録する） | 再現性のため差しかえが目的 |
| **純粋な計算関数** | **いけない** | 本物をリンクするか、実装を写す |
| **判定・分岐に使う値を返す関数** | **いけない** | 呼びだし側の制御フローが変わる |
| テスト対象が依存する業務ロジック | **いけない** | 代役にするとテストの意味が消える |

### 純粋関数をリンクできないとき

ファイル全体をリンクすると依存が芋づるで付いてくる場合、**実装を写す**。ただし写しは本体と乖離するので、次の 2 つを必ずやる。

1. **写しであることをコメントで明記する。** どのファイルの何行目から写したかを書く
2. **本物のふるまいを固定するテストを別に用意する。** 写しと本物が乖離したら、そのテストで気づける

```c
/* distance は代役にしてはいけない。misc3.c:2103 が
 * `while (distance(...) > dis)` でループするので、常に 0 を返すと
 * ループの意味が変わる。純粋関数なので misc1.c:210 の実装を写す。
 * tests/distance_test.c が本物のふるまいを 10 件で固定しているので、
 * 写しと本物が乖離すればそちらで気づける。 */
```

写した直後に、**本物と文字単位で一致することを確認する**（`sed` で両方を取りだして `cmp`）。手で写すと転記ミスが入る。

### 代役の見直しは定期的に

代役は増えるほど「何を潰しているか」が見えにくくなる。**項目をいくつか終えたら、代役の一覧を読みなおす。** 「常に 0 を返す」「常に false を返す」ものを探し、それが呼びだし側の判定に使われていないかを確かめる。

## モックは「渡された引数」も記録する

**戻り値を固定するだけのモックは、保護に穴を作る。**

```c
/* よくある形。だが不十分 */
int randint(int maxval) { (void)maxval; return fixed_value; }
```

これで固定できるのは「返る値」だけだ。**呼びだし側が渡した引数が正しいかは検証できない。** 上の例なら、`randint(16)` と書くべきところを `randint(15)` に取りちがえても、返る値が同じなのでテストは通ってしまう。配列の要素数を渡している場合、これは配列外アクセスの見逃しになる。

だから**引数と呼びだし回数を記録し、読みとれるようにする**。

```c
static int last_maxval = 0;
static int call_count = 0;

int randint(int maxval)
{
    last_maxval = maxval;     /* 何を渡されたか */
    call_count++;             /* 何回呼ばれたか */
    return fixed_value;
}

/* テストから読みとる窓口。本体には存在しない */
int fixture_randint_last_maxval(void) { return last_maxval; }
int fixture_randint_call_count(void)  { return call_count; }
```

記録は setUp（`fixture_reset()`）で消す。消さないと前のテストの値が残る。

### 何を記録する価値があるか

| 記録する対象 | 検出できる誤り |
|---|---|
| **引数の値** | 定数・添字・上限の取りちがえ（`randint(16)` → `randint(15)`） |
| **呼びだし回数** | 乱数列のずれ。**回数が変わると以後の乱数がすべてずれる**ので、ゲームやシミュレーションでは目に見えないふるまいの変更になる |
| **呼びだし順序** | 副作用の順序が意味を持つ場合（ログ出力、状態遷移） |

**呼びだし回数の記録はとくに価値が高い。** リファクタリングで「同じ計算を 2 回するようになった」ことは、戻り値だけ見ていると気づけない。純粋関数なら結果は同じだが、乱数や時刻のように**呼ぶこと自体が状態を変える**関数では、ふるまいが変わってしまう。

### ただしやりすぎない

記録するのは**そのテストで検証したい性質に関わるものだけ**にする。すべての引数を記録して毎回検証すると、テストが「モックが期待通り呼ばれたか」の確認に堕して、実装の内部構造に過敏になる（下記「モックの粒度」）。

判断の目安：**その引数が間違っていたら、本番で壊れるか。** 壊れるなら記録する価値がある。配列の上限、ファイルのモード、タイムアウト値などが該当する。

## モックが返す値

**モックには「ありそうな値」を返させる。** 実際の API が返さない値を返させたテストは、通っても何も保証しない。

正常系のほか、外部依存の失敗系（接続エラー、タイムアウト、不正なレスポンス、空のレスポンス）も返させる。外部依存の失敗は本番で必ず起きるが、モックなしではテストできない。**これはモック導入の最大の見返りだ。**

## 切りはなしのコストが見あわないとき

依存が絡みあっていて、切りはなしに大がかりな改造が必要な場合がある。その場合は無理をせず、次を検討する。

- **より外側でテストする。** 単体テストが書けないなら、その関数を含むより大きな単位でテストする。実 I/O を伴っても、保護がゼロよりはるかにマシだ。ただし遅いテストは実行されなくなるので、通常のテストと分けて実行できるようにする
- **テスト用の実体を用意する。** インメモリ DB、一時ディレクトリ、ローカルのテストサーバー。モックより手間はかからず、本物に近い
- **その項目を棚上げする。** 切りはなしコストが修正の価値を上回るなら、それは正当な判断だ。理由を記録してユーザーに報告する

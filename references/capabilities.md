# エージェント能力に応じた実行方式

このスキルの本質は **「テストで保護してから小さなステップで直す」** ことと **「コードを読む作業を本体の文脈から追い出す」** ことの 2 点にある。前者はどのエージェントでも同じだが、後者の実現方法は使えるツールによって変わる。

作業を始める前に、自分がどの層にいるかを判定する。

## 層の判定

| | サブタスクを起動できるか | 該当例 |
|---|---|---|
| **層 1** | できる（並行も可） | Claude Code（Task/Agent）、Codex CLI（並行タスク） |
| **層 2** | できない（単一の会話のみ） | GitHub Copilot（Chat/Edits/Agent モード）、Cursor、単発の CLI 実行 |

判断がつかない場合は**層 2 として振るまう**。層 2 の手順は層 1 でも正しく動く（遅いだけ）。逆は成立しない。

## 層 1：委譲する

`task-prompts.md` の指示文をサブタスクに渡す。本体（司令役）は実装ファイルを開かない。

- フェーズ 1 の検出は 2〜4 並行。担当を分けると視点が分かれて検出漏れが減る
- フェーズ 3 のステップ A / B / C は**別々のサブタスク**に割りあてる。同一タスクに A と B を任せると、テストを書いた本人が実装を変えることになり、自分の変更に合わせてテストを緩める誘惑が働く
- 本体が受けとるのは各 40 行以内の表と要約だけ

## 層 2：区切って捨てる

サブタスクが使えなくても、目的（本体の文脈を実装コードで埋めない）は達成できる。**作業を区切り、区切りごとに文脈を捨てる。**

やり方は次の通り。

1. **1 セッション 1 ステップに限定する。** フェーズ 3 の項目 #1 のステップ A を終えたら、そのセッションを終える。次のセッションでステップ B を始める。長い会話を続けず、意図的に切る
2. **セッションの冒頭で `REFACTORING_PLAN.md` を読む。** これが引き継ぎ書になる。前のセッションの会話内容を思いだす必要がない状態に保つ
3. **セッションの終わりに必ず計画ファイルを更新する。** 状態、テスト件数、次にやること。ここを書かずに終えると次のセッションが迷子になる
4. **`task-prompts.md` の指示文を、自分への指示として読む。** 「サブタスクに渡す文」ではなく「このステップで守る規則」として使う。返答量の制限は「調べた内容を会話に貼らない」という自己規律として読む
5. **ステップ C（検証）は必ず新しいセッションで行う。** 同じセッションで B の直後に検証すると、自分が書いた変更を「正しいはず」という前提で見てしまう。文脈を捨ててから、`git diff` とテスト出力だけを根拠に機械的に確認する

**ステップ C を新セッションで行うことが、層 2 で最も重要な規律。** ここだけは省略しないでほしい。層 1 が「別のサブタスクの目」で担保していた独立性を、層 2 では「文脈を捨てた自分の目」で代替する。

### 層 2 でのファイル読み

実装を読まざるをえない場合、次を守る。

- **1 ファイル全文を無条件に開かない。** まず対象の関数名で検索し、該当箇所とその前後だけを読む
- **読んだ内容を会話に貼りなおさない。** 要点を 3 行にまとめて計画ファイルに書き、原文は捨てる
- **テスト出力は件数と失敗名だけを見る。** 全文をスクロールして会話に残さない

## 出力量の制限

入力だけでなく**出力にも上限がある**。1 回の応答で書ける量には限りがあり、超えると書きこみそのものが失敗する。

**長いファイルを 1 回で書かない。** とくにステップ A のテストファイル（20〜40 件書くと数百行になる）と `REFACTORING_PLAN.md`（台帳・棚上げ・バグ候補・作業ログを含む）が危ない。

- **テストファイル**：まず骨格（取りこみ、補助関数、テスト 2〜3 件）を書いてグリーンを確認し、以後は数件ずつ追記する。追記のたびに動かす
- **計画ファイル**：節ごとに独立した追記にする（`plan-template.md`「書きだし方」）。長い表は 1 回 15 行まで
- **ユーザーへの報告**：全項目が終わってから長大な総括を書こうとすると書ききれない。3 項目ごとに数行ずつ出す

**この分割は「1 コミット 1 変更」と同じ発想。** 各段階でグリーンを確認するので、どのテストを足したときに壊れたかが即座にわかる。一度に 40 件書いてまとめて動かすより原因の切り分けが速い。出力上限への対処が、たまたま作業の安全性も高めている。

**担当が上限超過で止まったとき**は作業が中途で残る。(1) テストがグリーンか確認する、(2) 中途の成果に価値があればまずコミットして固定する、(3) コメントと実装が食いちがっていないか確認する（途中で止まった作業は「コメントは書いたが実装が伴っていない」状態になりやすい）、(4) 残りを新しい担当に任せ、どこまで終わっているかを明示する。

## どちらの層でも守ること

- `REFACTORING_PLAN.md` が唯一の正本。会話履歴を正本にしない
- 1 コミット 1 変更。各コミット後にテストを実行してグリーンを確認
- テストの assertion を変更しない
- 3 項目ごとにユーザーへ中間報告

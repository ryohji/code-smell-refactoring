# 言語パック：C / C++

コアの手順（`SKILL.md`、`refactoring-loop.md`、`patterns.md`、`dependency-breaking.md`）
に対する C / C++ 固有の補足。**対象が C / C++ のときだけ読む。**

## 1. リンクシーム：本体を 1 行も変えずに保護する

**C でまず検討するのはこれ。** リンク時にシンボルが解決される言語では、
テスト実行形式に何をリンクするかを選ぶだけで依存を差しかえられる。
`dependency-breaking.md` のパターン A・B は本体に手を入れる（インターフェース
導入、引数追加）が、この手法は**本体を無変更のまま保護できる**ので、
「テストのないコードは触らない」という原則との相性が最もよい。

対象：グローバル変数・シングルトン・巨大なデータテーブルに依存する関数。

1. **対象を含む `.o` だけをコンパイルする。** ファイル単位で切りだす
2. **リンクして未解決シンボルの一覧を得る。** これが「対象が必要とするもの
   すべて」の正確な一覧。推測せずリンカに教えてもらう
3. **一覧を 3 つに分類する**
   - 本物をリンクできるもの（定数表、純粋な計算関数）→ その `.o` を足す
   - テスト用に用意すべきデータ（グローバル変数、状態を持つ配列）→ フィクスチャに定義
   - 代役で足りるもの（画面出力、乱数、ファイル I/O）→ フィクスチャにスタブ
4. フィクスチャにテスト専用の初期化関数を足す
5. リンクが通ったらテストを書く

```bash
cc -std=c17 -Isrc -c -o /tmp/target.o src/target.c
cc -o /tmp/t test.c /tmp/target.o 2>&1 \
  | grep 'undefined reference' | sed 's/.*undefined reference to //' | sort -u
```

**この一覧が設計の出発点。** 何をモックすべきかを頭で考える必要がない。

**向かない場面**：ヘッダに `static inline` で書かれた関数、マクロで展開される
処理。プリプロセッサの段階で確定するのでリンクシームでは差しかえられない。
その場合はパターン A・B に戻る。

### フィクスチャモジュールの要点

```c
/* tests/fixture.c -- テスト用のグローバルデータと初期化関数 */
#include "types.h"

state_type state;      /* 本体では巨大データと同居していて切りだせない */

/* テスト専用。オリジナルには存在しない。setUp から呼ぶ */
void fixture_reset(void) {
    extern item_type table[];
    memset(table, 0, sizeof(item_type) * TABLE_SIZE);
    memset(&state, 0, sizeof state);
}

void msg_print(char *str) { (void)str; }   /* 画面出力は捨てる */
```

- **本物のデータ表は本物をリンクする。** 数百行の定数表を写すと本体と乖離する
- **フィクスチャは最小限に。** 本体と一緒にリンクできないものだけを定義する。
  `multiple definition of ...` が出たら、それは本物をリンクできるということ
  なのでフィクスチャから消す
- **テスト専用の関数を足してよい。** `fixture_reset()` は本体に存在しない。
  テスト用モジュールの中にあるので本体の実装には影響しない。これがこの手法の
  要点で、本体を汚さずにテスト環境を作れる
- **`fixture_reset()` は setUp から呼ぶ。** グローバル状態を使うテストは前の
  テストの影響を受けると実行順で結果が変わる

### 参照箇所をポインタ経由に置きかえる小技

```c
/* 変更前 */ extern state_type state;
/* 変更後 */ extern state_type *state_ptr;
             #define state (*state_ptr)
```

マクロで元の記法を保てば、参照箇所（数百箇所ありうる）を書きかえずに済む。
ただし本体への変更なので「本体無変更」は崩れる。リンクシームで足りるなら
そちらを選ぶ。

## 2. 関数ポインタの組で API を差しかえる

標準ライブラリや OS API への依存。`dependency-breaking.md` のパターン B の
C での書きかた。

```c
struct file_op {
    FILE*  (*open)(const char*, const char*);
    size_t (*read)(void*, size_t, size_t, FILE*);
    int    (*close)(FILE*);
};

void *decrypt_file(void *secret, const char *path, struct file_op file_op) {
    FILE *fp = file_op.open(path, "rb");
    ...
}
```

**引数を増やせない場合**（呼びだし元が多すぎる、公開 API である）:

- **既存シグネチャを保つラッパーを残す。** `decrypt_file(secret, path)` は
  本物の `file_op` を渡して新しい関数を呼ぶだけにする。呼びだし元は無変更
- **差しかえ可能なグローバルにする。** `static struct file_op g_op = {fopen,
  fread, fclose};` をテストから差しかえる。**teardown で必ず元に戻す。**
  戻さないと後続のテストが汚染され、実行順で結果が変わる最悪のテストになる

## 3. 真偽を値として返すときは明示する

条件式をそのまま返すと、返る値が何かが読み手に伝わらない。

```c
/* 悪い：1 が返る根拠が「== の結果は 0 か 1」という規格の知識に依存する */
return (turn % (2 - speed)) == 0;

/* よい：返す値そのものを書く */
return (turn % (2 - speed)) == 0 ? 1 : 0;
```

とくに**戻り値の型が `bool` ではなく `int` の場合**、読み手は「真偽か、それとも
個数か」を判断できない。

**`_Bool` と `int` の違いは実害を生む。** `bool` は代入時に 0/1 に正規化される
が、`int` を返す関数では正規化されない。`(a & FLAG)` をそのまま返すと真のとき
フラグの値そのもの（`0x80` など）が返る。**呼びだし側が `== 1` で比較していると
壊れる。** 検出フェーズで「複雑な条件分岐」を見るときは、この形を探す。

## 4. ガード節にしない分岐の例

`patterns.md`「6. 複雑な条件分岐」の判断表を C で書くとこうなる。

```c
/* 悪い：どちらも正常な結果なのに、片方が「例外的」に見える */
static int moves_this_turn(int16_t speed) {
    if (speed > 0) { return speed; }
    return (turn % (2 - speed)) == 0 ? 1 : 0;
}

/* よい：if/else で対等に並べる。または三項演算子で式として書く */
static int moves_this_turn(int16_t speed) {
    return speed > 0 ? speed
                     : (turn % (2 - speed)) == 0 ? 1 : 0;
}
```

## 5. ヘッダとビルドの落とし穴

C ではリファクタリングの失敗がテストではなく**ビルド**に現れる。着手前に確認する。

- **多重取りこみの番人（include guard）がないヘッダがある。** 古いコードでは
  型定義ヘッダに `#ifndef` がないことがある。この場合、テストから重ねて
  include できない。**新しく作るモジュールのヘッダは型定義ヘッダを include
  せず**、「先に X, Y, Z を include すること」を前提としてコメントに書く
  （既存の全域ヘッダがそうなっているなら、それに合わせる）
- **include の順序に意味がある。** 全域ヘッダが単体でコンパイルできないことは
  珍しくない。既存ファイルの並び順をそのまま踏襲する
- **全域ヘッダが標準関数を差しかえていることがある。** `#define fopen tfopen`
  のようなマクロがあると、テストで実ファイルを開く手が塞がれる。
  `tmpfile()` を使うか、そのヘッダを include しない
- **新しい `.c` はビルド定義に登録する。** ソース一覧とオブジェクト一覧の
  **両方**、および依存行。ここを忘れるとテストはグリーンなのに本体がリンク
  できない（`SKILL.md`「テストがグリーンでも、動くとは限らない」の典型例）
- **`static` 関数を直接検証したいときは、テスト側が `.c` を丸ごと
  `#include` する。** ただしフィクスチャ側に同名の定義があると二重定義で
  壊れるので、その定義は消す

## 6. テスト実行形式は「1 実行形式 1 対象モジュール」

C では 1 つの実行形式に全テストを詰めると、リンクする `.o` が増えて依存が
芋づるで付いてくる。**対象モジュールごとに実行形式を分ける**と、各テストが
必要最小限のリンクで済み、「このモジュールは何に依存しているか」がビルド
定義から読める。

この形にすると、**新しく切りだしたモジュールが全域ヘッダを include して
いなければ、テストはその 1 ファイルだけをリンクして通る。** 逆に言えば、
モジュールを切りだすときに依存を持ちこまないことが、テストの軽さに直結する
（`patterns.md`「8. データの散在」の「窓口モジュールを作る」を参照）。

## 7. この言語での「完了」の形

C でデータの散在・強すぎる依存を直したときの到達点は、**対象を `.c` 内の
`static` にし、全域ヘッダの `extern` 宣言を消せた状態**。ここまで進めると
コンパイラが「外から触れない」ことを保証するので、以後の変更が波及しない。

途中（窓口を作ったが `extern` は残っている）で止めると、新旧 2 つの経路が
併存する。**1 項目の終わりは `extern` を消すところまで**と決めておく。

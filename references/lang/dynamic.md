# 言語パック：動的言語（Python / JavaScript / TypeScript / Ruby ほか）

コアの手順に対する補足。**対象がこれらの言語のときだけ読む。**

## 1. モジュール差しかえが C のリンクシームに相当する

`dependency-breaking.md` のパターン C（本体を無変更のまま保護する）は、
これらの言語ではモジュールの差しかえ機構が担う。

| | 差しかえ手段 |
|---|---|
| Python | `unittest.mock.patch`（対象が**参照している名前**を差しかえる） |
| JS / TS | `jest.mock`, `vi.mock`（モジュール解決を差しかえる） |
| Ruby | 特異メソッドの定義、RSpec の `allow(...).to receive` |

**要点：差しかえるのは「定義された場所」ではなく「使われている場所」。**
Python で `from os import getcwd` と取りこまれていたら `patch('os.getcwd')`
では効かない。`patch('対象モジュール.getcwd')` と書く。ここを外すと本物が
呼ばれ、テストが通ったのに保護できていない状態になる。

**本体を変えずに済むならそれが最も安全**なので、引数追加や依存注入より先に
この手段を検討する。

## 2. 型がないぶん、テストが唯一の保護になる

静的型のある言語では、シグネチャを変えるとコンパイラが呼びだし側の漏れを
教えてくれる。動的言語ではそれがない。だから次を守る。

- **シグネチャを変える項目は、呼びだし側の grep 結果を数えてから着手する。**
  「何箇所ある」を先に確定させる。1 箇所ずつ直して 1 コミット
- **キーワード引数・省略可能引数の追加**を優先する。位置引数の順序変更や
  削除は、呼びだし漏れが実行時まで見つからない
- **文字列経由の参照を疑う。** `getattr`, `eval`, デコレータ、設定ファイルの
  クラス名、URL ルーティング、テンプレート内の属性参照。`patterns.md`
  「9. 不要なコード」の裏取りで grep が効かない典型
- 型ヒント／`.d.ts` があるなら、型チェッカ（mypy, tsc）を**テストと並べて
  実行する**。これは「1 コマンドで実行できるテスト」の一部と考えてよい

## 3. この言語で起きやすい落とし穴

- **取りこみ時に副作用が走る。** モジュールを取りこんだだけで設定読みこみや
  接続が起きると、テストの収集自体が失敗する。副作用を関数の中に押しこむのが
  最初の 1 項目になることがある
- **可変な既定引数**（`def f(x=[])`）。リファクタリング中に「同じ値が共有
  されている」ことに気づいて直したくなるが、**それはふるまいの変更**。
  バグ候補として記録する
- **モンキーパッチを戻し忘れる。** `patch` はコンテキストマネージャ／
  デコレータで使う。手で差しかえたら teardown で必ず戻す。戻さないと実行順で
  結果が変わる最悪のテストになる
- **可視性の言語機能が弱い。** `_` 始まりや `#private` は規約に近い。
  公開範囲を絞る作業（`patterns.md`「7. モジュール分割」の 4 番）の到達点は
  `__all__` の定義、パッケージの `index` からの除外、リンタ規則になる

## 4. モジュールはファイル 1 つ（またはパッケージ 1 つ）

`patterns.md`「3. 肥大化クラス／モジュール」の単位は、クラスがあってもファイルに
複数のクラスを置ける言語では**ファイルとパッケージの両方**で見る。`utils.py`
`helpers.js` `common/` は、C の `misc.c` とまったく同じ理由で育つ。

この言語での固有の注意。

- **移動が参照を壊す。** ファイル間で関数を移すと取りこみ文が変わる。静的型が
  ないので、**漏れは実行時にしか出ない**。移す前に取りこみ元を grep で数え、
  1 箇所ずつ直して 1 コミット
- **文字列経由の参照が移動を壊す。** 設定ファイルのクラス名、`importlib`、
  URL ルーティング、プラグイン登録。grep では拾えない形なので、移すファイルの
  名前そのものを全文検索する
- **後方互換の再取りこみ（re-export）を残したくなるが、期限を決める。**
  `from .new_module import *` を旧ファイルに残すと移動は無痛で済むが、
  **新旧 2 つの経路が併存する状態**で、`patterns.md` の「元のファイルが
  無くなることを終点にする」に反する。残すなら、消すところまでを 1 項目にする
- **移動の副産物として循環取りこみが出ることがある。** 出たらそこが本当の
  結合点だ。切り目を変えるか、共通部分を第三のモジュールに出す

## 5. この言語での「完了」の形

型でも可視性でも縛れないので、**到達点は「そのデータ／処理を知っている箇所の
数」で測る。** 着手前に grep で数えておき、終わりにもう一度数える。
「12 箇所が触っていたものが窓口 1 つになった」が成果の記述になる。

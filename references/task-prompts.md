# 作業ステップの指示文

`{{...}}` を実際の値に置きかえてサブタスクに渡す（層 1）か、自分への規律として読む（層 2）。

`{{言語パック}}` には、フェーズ 0 で選んだパックのパス（例
`{{スキルパス}}/references/lang/c.md`）を入れる。該当パックが無い言語なら
「該当パックなし」と書く。

## 共通ルール：返答量の制限

すべての指示文に次を含める。層 1 ではサブタスクへの制約として、層 2 では自分への規律として使う。これがないと長いコードが文脈を埋め、作業を区切った意味がなくなる。

```
【返答形式の厳守】
- 指定された表・箇条書きの形式だけを返す。前置き・所感・励ましは書かない。
- コード断片の引用は 1 箇所につき 3 行以内。長い引用のかわりに `path:行番号` を書く。
- ファイル全文、テスト出力の全文、差分全体を返さない。件数と要点だけを書く。
- 表は指定された件数まで。件数を増やすより、1 行を短くすることで情報量を保つ。
```

**行数の上限を機械的に決めない。** 「全体で N 行以内」と書くと、最も価値のある情報（テストの足場になる関数、抽象化の形など、次の判断を左右するもの）が削られることがある。制限すべきなのは**長さそのものではなく、読み捨てる情報**だ。

だから制限は次の 2 段構えにする。

1. **表の行数を指定する**（例「上位 12 件まで」）。これで分量の大枠が決まる
2. **判断に直結する項目は別枠で明示的に求める**（例「テストが書きやすい純粋関数を 3〜5 個」）。別枠にしておけば、表の制限に押されて消えない

この形にすると、返答は表 12 行 + 別枠 5 項目 + 総計 1 行で 25 行程度に収まり、しかも最重要の情報が確実に含まれる。

## 一度に受けとる量を分ける

複数の担当を並行させるとき、**全員の報告が同時に届くと合計が大きくなる**。1 担当 25 行でも 4 担当なら 100 行だ。

対策は 2 つ。

- **報告が届いたそのつど、計画ファイルに転記する。** 溜めて一括処理しない。転記したら、その報告内容は文脈から捨ててよい
- **書きこみも分割する。** 4 担当分の台帳を 1 回で書こうとすると出力の上限に当たる。P1 の表、P2 の表、棚上げ、と節ごとに追記する（`plan-template.md` の「書きだし方」を参照）

## 担当にも「小さく書け」と指示する

出力の上限は担当側にもある。ファイルを作る作業を含む指示文には、次の 1 文を必ず入れる。

```
長いファイルを 1 回の応答で書かないでください。骨格（取りこみ・補助関数・テスト
2〜3 件）を書いてグリーンを確認し、以後は数件ずつ追記して、追記のたびに動かして
ください。出力の上限を超えると書きこみ自体が失敗し、作業が中断します。
```

理由と、担当が途中で止まったときの引き継ぎ手順は `capabilities.md`「出力量の制限」。

## 臭いの検出（フェーズ 1）

```
{{対象範囲: 例 src/parser/ 以下の全ファイル}} を調査し、次に挙げるコードの臭いを検出して報告してください。
実装の変更は一切しないでください。読むだけです。

【探す臭い】
1. 重複コード — 同じ処理が複数箇所に存在する。似ているが微妙に違うロジックが散在している
2. 長すぎるメソッド — ひとつの関数が長く、理解しにくい
3. 肥大化クラス／モジュール — クラスが複数の責務を持つ。クラスのない言語ではファイル（`.c`、モジュール）が単位
4. 不適切な責務配置 — 処理やデータが正しい場所にない
5. 名前が意図を表さない — 名前から役割が読みとれない、マジックナンバー
6. 複雑な条件分岐 — ネストが深い、分岐が乱立している
7. 強すぎる依存関係 — 修正時の影響範囲が広い、モジュール間結合が強い
8. データの散在 — 複数のクラスに同じデータ構造が重複
9. 不要なコード — デッドコード、使われない変数・関数・クラス、古い定義
10. 理解しづらいロジック — コメントなしでは意図が不明

【判断の指針】
- 「臭いが濃い」ことと「直す価値がある」ことは別です。触られないコードの臭いは実害が小さい。
  変更頻度（git log で確認）と参照の広さ（grep で確認）を根拠に影響度を判定してください。
- 対象関数がテストで保護されているかを確認してください。テストファイルの存在ではなく、
  その関数を通るテストが実在するかを見ます。保護の有無が着手コストを大きく左右します。
- 「デッドコード」と判定する前に、次の 2 段階で裏取りしてください。
  1. 名前を全文 grep する。動的呼びだし、リフレクション、設定ファイル経由の参照、
     外部公開 API、ビルド対象外ファイルからの参照の可能性があります。
  2. **git 履歴で導入意図を確認する。**
     `git log --oneline --follow -- <ファイル>` と `git log --oneline -S '<関数名>'` を実行し、
     導入コミットのメッセージを読んでください。
  参照ゼロは「不要」の証明になりません。未使用のコードには「本当の残骸」と
  「先行して用意された基盤」の 2 種類があり、後者を消すと進行中の作業を壊します。
  コミットメッセージに `foundation`, `scaffold`, `prepare`, 「基盤」「準備」などの語があるもの、
  および**直近も変更されているのに参照ゼロ**のものは、残骸ではなく足場と考えてください。
  この場合は「未接続の基盤（削除非推奨）」と分類し、導入コミットのメッセージを根拠欄に書いてください。
  裏取りできないものは「デッドコードの疑い（未確認）」と書いてください。
- 「重複コード」は差異が意図的である場合があります。差異の内容を 1 行で書いてください。
- **モジュール（ファイル）の名前も臭いの対象です。** 何も約束していない名前
  （`misc` `util` `common` `helper` `manager` `stuff`）と連番（`misc1` `misc2`）は、
  中身を読む前に候補になります。**該当ファイルについては「このファイルは何のために
  あるか」を 1 文で書いてみて、書けなければ責務の一覧を返してください**（塊ごとに
  関数名と行数）。ファイル冒頭のコメントが責務を並べていることが多いので、まず読みます。
  分類は「3. 肥大化クラス／モジュール」です（名前だけの問題ではないので 5 には入れない）。

【返す表】
| # | 分類 | 場所(path:行) | 内容(1-2文) | 影響度 | コスト | 保護 | 根拠 |
影響度は High/Medium/Low。コストは Low/Medium/High。保護は 有/薄/無。
根拠は影響度をそう判定した理由を 1 行（変更頻度、参照数など具体的な数字を入れる）。

影響度の高い順に上位 12 件まで。件数の総計は分類別に別途 1 行で書いてください。

【別枠：テストの足場になる関数（必ず答えてください）】
テストが書きやすい関数を 3〜5 個挙げてください。関数名・シグネチャ・依存の有無を明記します。
条件は「引数だけから戻り値が決まる」こと。グローバル変数、乱数、時刻、I/O、
外部ライブラリに依存しない関数が理想です。被参照数も書いてください。

この項目が最も価値のある情報です。テストが 1 件も無い状態では、
どの修正も「壊したかどうか」を確認できません。だから最初に必要なのは
「テストが書けて、動いて、レッドが出る」ことを確立できる関数で、
そのために依存の少ない関数を見つけることが検出作業の最大の目的になります。

表の件数制限に押されてこの項目を削らないでください。別枠にしているのはそのためです。

【別枠：テストを妨げている依存（あれば）】
対象範囲にモック差しこみ口（関数ポインタの構造体、インターフェース、
差しかえ可能なグローバル）が既にあるかを報告してください。
あれば、その形を 3 行以内で示してください。既存の差しこみ口が使えるなら、
外部依存を持つ関数もテスト可能になり、優先度の判断が変わります。

【言語固有の手引き】
対象言語のパックがあれば先に読んでください（{{言語パック}}）。無い場合はコアだけで
進め、足りないと感じた点を報告に 1 行で書いてください。

{{共通ルール：返答量の制限}}
```

## テストで保護する（ステップ A）

```
{{対象: 例 src/parser/config.py の parse_config 関数}} にテストを追加してください。
目的は現在の実装の保護です。実装のふるまいは変えないでください。

【手順：実装に答えを教えてもらう】
期待値を自分で計算しようとしないでください。テストフレームワークに教えてもらいます。
1. 空のテスト関数を追加してビルド／収集を通す
2. 対象関数の呼びだしを追加して通す
3. 戻り値の期待値を適当に決めて assert する
4. テストを動かす（失敗する）
5. テストが表示した実際の値で期待値を書きかえる
6. テストを動かす（成功する）
7. テスト名を、成功した assertion の内容を表す名前に変更する

【テストの書き方】
詳細は {{スキルパス}}/references/refactoring-loop.md の「良いテストの条件」を
読んでください。とくに次の 4 つを守ります。
- テスト 1 つに assert 1 つ。失敗した assert 以降は実行されないので、複数あると
  原因の切り分けに何往復もかかります。
- テスト名が assertion の説明になるように書く。名前が書けないなら目的が絞れていない証拠です。
- テスト内に条件分岐もループも書かない。引数で条件を確定させてください。
- 三角測量：引数 1 つにつき最低 2 ケース。1 ケースでは「まぐれ当たり」で通ることがあります。

【対象が外から呼べない場合】
対象のロジックが関数の中に直に書かれていて呼びだせないなら、「実装に答えを
教えてもらう」方式は使えません。**変更前の字面をテストの中に写しとり**、新しい
実体と総当たりで突きあわせてください。手順は refactoring-loop.md の
「変更前のロジックをテストに写す」を読んでください。

【保護が効いていることの確認】
テストを足しおえたら、保護したはずの箇所を意図的に 1 つ壊し（定数を 1 ずらす、
条件を反転する、順序を入れかえる）、**レッドになることと、その件数**を確かめて
ください。確認後は必ず元に戻し、グリーンに復帰することまで見ます。
レッドにならなければ、そこは保護されていません。件数は報告に書いてください。

【依存の切りはなし】
再現性を妨げる依存（ネットワーク、DB、ファイルシステム、シングルトン、現在時刻、乱数）が
あればモック化してください。ただし粒度は最小限に。何でもモックすると、テストが
「モックが正しく呼ばれたか」の確認になり、実装変更に過敏に壊れます。
切りはなしのために実装に手を入れる必要がある場合（引数の追加、インターフェースの導入）は、
その変更だけで一度テストをグリーンにしてコミットしてから、テストを足してください。
方法は {{スキルパス}}/references/dependency-breaking.md を参照。

【記録した値が怪しい場合】
実装のバグをそのまま「正しい値」として固定してしまうリスクがあります。
記録した値が仕様として不自然だと感じたら、テストにコメントを残してください。
  例: # TODO: 仕様確認 — 空入力で 0 を返すのは意図的か不明
そして報告に SUSPICIOUS として挙げてください。**ここでは直さないでください。**
現状を固定しないと、あとで「壊したのか元からか」が判別できなくなります。

【テストファイルを書くときの分割】
長いファイルを 1 回の応答で書かないでください。骨格（取りこみ・補助関数・main・
テスト 2〜3 件）を書いてグリーンを確認し、以後は数件ずつ追記して、追記のたびに
動かしてください。どのテストを足したときに壊れたかが即座にわかります。

【テスト実行コマンド】
{{テスト実行コマンド}}

【完了条件】
- 対象関数を通るテストが存在しグリーン
- テスト件数が増えている
- 実装のふるまいを変えていない
- コミット済み（メッセージ例: test: parse_config のテストを追加）

【返す報告】
- 追加したテスト件数と、テストファイルのパス
- テスト名の一覧（名前だけ。本文は不要）
- モックした依存とその理由（あれば）
- 依存切りはなしのために実装に加えた変更（あれば、1-3 行）
- SUSPICIOUS 項目（あれば、それぞれ 1 行）
- テスト実行結果の要約（件数、pass/fail/skip の数のみ）

【言語固有の手引き】
対象言語のパックがあれば先に読んでください（{{言語パック}}）。無い場合はコアだけで
進め、足りないと感じた点を報告に 1 行で書いてください。

{{共通ルール：返答量の制限}}
```

## 書きかえる（ステップ B）

```
{{対象: 例 src/parser/config.py の parse_config 関数}} をリファクタリングしてください。
臭いの分類は「{{分類: 例 長すぎるメソッド}}」、適用する手法は「{{手法: 例 メソッド分割}}」です。

この対象はすでにテストで保護されています（テストファイル: {{テストパス}}）。

【守ること】
1. 1 コミット 1 変更。各コミットの直後にテストを実行し、グリーンを確認してからコミットする。
2. レッドになったら、直そうとせず直前のコミットに戻してください。
   「あと少しで直る」と思って進めると複数の変更が絡んで原因を特定できなくなります。
   戻してやりなおすほうが速い。
3. テストの assertion（期待値）を変更しないでください。
   リファクタリングとは外部から見たふるまいを変えずに内部構造を改善することなので、
   テストも変わらないはずです。期待値を変えたくなったら、それはふるまいを変えている
   証拠なので、実装を戻して報告してください。
   シグネチャ変更にともなうテスト側の呼びかたの修正は許容します（期待値はそのまま）。
4. テストを削除・skip・無効化しないでください。
   （例外：非公開の補助関数が消えるなら、その関数専用のテストは一緒に消してよい。
     消した場合は報告に明記してください）
5. ふるまいを変える変更を混ぜないでください。
   バグを見つけても直さず、報告に「バグ候補」として挙げてください。「ついで」の修正は、
   テストがグリーンなのに動作が変わるという最悪の状態を招きます。
6. リファクタリングツール（IDE の自動リネーム・自動抽出）が使えるなら使ってください。
   機械的な変換は手作業より段違いに安全です。

【手法ごとの具体手順】
{{スキルパス}}/references/patterns.md の「{{分類}}」の節を読んでから着手してください。

【テスト実行コマンド】
{{テスト実行コマンド}}

【返す報告】
- コミットの一覧（各 1 行：コミットメッセージ + 何をしたか）
- 各コミット時点のテスト結果（件数と pass/fail/skip のみ）
- 変更したファイルと、増減した行数
- 途中で戻した回数と、その理由（あれば 1 行）
- バグ候補（あれば 1 行ずつ）
- 予定と違えた点（あれば。当初の手法が不適切だと判明した場合など）

【言語固有の手引き】
対象言語のパックがあれば先に読んでください（{{言語パック}}）。無い場合はコアだけで
進め、足りないと感じた点を報告に 1 行で書いてください。

{{共通ルール：返答量の制限}}
```

## 検証する（ステップ C）

```
直前に行われたリファクタリングを検証してください。**修正はしないでください。**
あなたの役目は、変更が本当にふるまいを保っているかを独立した目で確認することです。

対象コミット範囲: {{開始コミット}}..HEAD
リファクタリングの内容: {{1 行の説明}}
テスト実行コマンド: {{テスト実行コマンド}}
保護前のテスト件数: {{件数}}

【確認する 5 点】
1. テストがグリーンか。上のコマンドをそのまま実行して確かめる。
2. テスト件数が減っていないか。上記の保護前件数と現在の件数を比較する。
   減っていればテストが消されています。
3. skip / xfail / disabled が増えていないか。グリーンに見せるための無効化を探す。
4. テストの assertion が変わっていないか。テストファイルの差分（git diff）を見て、
   期待値が書きかえられていないかを確認する。
   - 許容：呼びかたの変更（引数の増減、関数名の変更、import の変更）
   - 違反：期待値そのものの変更、assert の削除、assert の緩和（equal → not none など）
5. ふるまいを変える変更が混ざっていないか。実装差分を見て、条件の追加・削除、
   エラー処理の変更、デフォルト値の変更、境界の変更など意味を変える変更がないかを見る。
   純粋な移動・抽出・改名・インライン化以外の変更はすべて疑ってください。

6. **テストが本当にこの変更を検証しているか（保護の穴の確認）。**
   グリーンであることは「テストが変更を見ている」ことを意味しません。
   変更した箇所を意図的に 1 つ壊し、レッドになることを確かめてください。
   **確認後は必ず元に戻し、グリーンに復帰することまで確認します。**

   レッドにならなかった場合、それは**テストの穴**です。よくある原因:
   - モックが引数を無視している（`int randint(int max) { (void)max; return 1; }` のような形。
     上限を取りちがえても返る値が同じなので検出できない）
   - テストが結果だけを見て、呼びだし回数や順序を見ていない
   - 変更した分岐を通る入力がテストに含まれていない

   穴が見つかったら**報告してください。** 埋めるのは次の担当の仕事ですが、
   「グリーンだが保護されていない」状態を見逃すと、以後の変更が無防備になります。

【返す報告】
| # | 確認項目 | 判定 | 根拠 |
判定は OK / NG。NG は根拠に具体的な場所（path:行）を書く。
最後に 1 行で総合判定（PASS または FAIL）。FAIL の場合は最も重大な違反を 1 行で。

{{共通ルール：返答量の制限}}
```

## 仕様起こし（フェーズ 4）

```
{{対象: 例 src/parser/config.py}} の実装とテストから、モジュールの仕様をまとめてください。
コードは変更しないでください。読んで書くだけです。

【まとめ方：偏微分 × 三角測量】
テストは「動かして確かめられる仕様」です。個々のテストは仕様の具体例ひとつを表しています。
複数の引数のうちひとつだけをパラメーターとして動かしているテスト群を見つけ、
「XXX のとき YYY と動く」という形の仕様文に還元してください。
例: test_send_hello_accepted と test_send_bye_rejected（第 2 引数は DefaultServer 固定）
  → 「DefaultServer に対して、hello は受理され OK を返す。bye は拒否され NG を返す。」

【網羅しようとしないこと】
引数の組みあわせはほぼ無限にあります。書ききれない量を目指すと途中で破綻し、
```

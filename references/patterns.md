# 臭い別のリファクタリング手順

自分が担当する分類の節だけを読む。各節は「小さなステップに分割された手順」の形で書かれている。**手順の 1 行が 1 コミットに対応する。** 各行のあとにテストを実行してグリーンを確認する。

用語は「クラス」「インターフェース」で書いてあるが、**その言語にある近いものに読みかえる**（モジュール、構造体＋関数群、プロトコル、型クラス）。言語固有の書きかたと落とし穴は `lang/` の該当パックにある。

## 1. 重複コード

### メソッド抽出（Extract Method）

1. 重複箇所のひとつを選び、その範囲を新しい関数として抽出する。元の場所は呼びだしに置きかえる
2. 他の重複箇所を、抽出した関数の呼びだしに 1 箇所ずつ置きかえる（**箇所ごとに 1 コミット**）
3. 抽出した関数に、意図を表す名前をつける（自動リネームが使えれば使う）

**差異がある場合。** 完全一致でない重複は、差異を引数として外に出す。差異が「処理の一部」なら、その部分を関数（コールバック、ラムダ）として受けとる。**差異が 3 つ以上になったら抽出をやめる。** 引数だらけの関数は、重複よりも読みにくい。

### クラス抽出（Extract Class）

重複したロジックが状態（複数のフィールド）を伴う場合。

1. 新しいクラスを作り、空のまま既存クラスから参照できるようにする
2. 関係するフィールドを 1 つずつ新クラスへ移す。元のクラスには委譲を残す
3. 関係するメソッドを 1 つずつ新クラスへ移す
4. 委譲が不要になった箇所を、呼びだし側から直接新クラスを使うように書きかえる
5. 元のクラスから空になった委譲を削除する

### テンプレートメソッド導入

似た処理の「骨格は同じで一部が違う」場合。骨格を親クラス（または高階関数）に、差分をサブクラス（または引数の関数）に置く。

1. 骨格を持つ親クラスを作り、差分部分を抽象メソッドとして宣言する
2. 既存の実装のひとつをサブクラス化し、差分だけを実装する。テストで確認
3. 残りの実装を 1 つずつサブクラス化する

**継承が重い場合は高階関数で足りる。** 差分が 1 箇所なら、関数を引数で渡すほうが読みやすい。

## 2. 長すぎるメソッド

### メソッド分割

**行数で機械的に割らない。** 意味のある単位で切る。切り目の見つけ方は次の通り。

- **コメントがある行。** 「// ヘッダーを検証」というコメントは、そこが 1 つの意味の塊である印。抽出してコメントを関数名にする
- **ローカル変数のスコープ。** ある変数が使われ始めて使われ終わるまでの範囲は、1 つの塊である可能性が高い
- **空行で区切られた段落**
- **ネストの塊**（`if` ブロックの中身、ループの本体）

手順：

1. 抽出する範囲を決める。その範囲が使う変数（入力）と、範囲のあとで使われる変数（出力）を確認する
2. 出力が 1 つなら、それを戻り値とする関数として抽出する
3. 出力が 2 つ以上なら、まずそれらをまとめる型（構造体、タプル、データクラス）を導入するか、そもそも切り目を変える
4. 抽出したら、名前が「何をするか」を語っているか確認する。語れないなら切り目が悪い。戻して切り直す

**抽出した関数の引数が 5 つを超えたら、切り目が悪い。** 関連するデータをまとめる型が足りていない可能性が高い。

### メソッドインライン化

薄すぎる関数（1 行を呼ぶだけ、名前が呼び先と同じ）は、かえって読みにくい。呼びだし箇所に展開して削除する。

1. 呼びだし箇所を 1 つずつ本体に置きかえる
2. 呼びだしがなくなったら関数を削除する

## 3. 肥大化クラス／モジュール

### 責務の見つけ方

**フィールドとメソッドの利用関係を見る。** メソッド群 A がフィールド群 X だけを使い、メソッド群 B がフィールド群 Y だけを使っているなら、そこに 2 つの責務がある。この「使う／使わない」の関係が分割線だ。

**クラスのないモジュール（ファイル）では、フィールドの代わりに次を見る。**

- **ファイル内に閉じた状態** — ファイル先頭の非公開変数、そのファイルだけが
  触るデータ表。「どの関数がどれを使うか」がそのまま分割線になる
- **呼びだし元の集合** — 関数群 A が画面からだけ呼ばれ、B が生成処理からだけ
  呼ばれているなら、A と B は別の層に属している
- **取りこみの並び** — そのファイルが何を必要としているか。塊ごとに必要な
  取りこみが違うなら、分けたときに依存が減る
- **名前の接頭辞** — `prt_*` `inven_*` `stat_*` のように揃った接頭辞は、
  書いた人が塊を認識していた証拠。ほぼそのまま新しいモジュール名になる

### 1 文で言えるかを試す

**分割が必要かは「このファイルは何のためにあるか」を 1 文で書いてみればわかる。**
「〜と〜をする」「〜に関するいろいろ」しか書けないなら、接続詞の数だけ責務が
ある。**逆に、書けた 1 文がそのまま新しいモジュール名になる。**

### モジュール分割と再命名

「1 つのファイルが複数のことをしている」形。移動そのものは切り取って貼るだけで、
テストで保護されていれば安全な部類に入る。**難しいのは切り目を決めることと、
やりきることだけだ。**

1. **棚おろしをする。** ファイル内の全定義を、名前・行数・使っている状態・
   呼びだし元とともに一覧にする。数が多いので機械化する（スクリプト 1 本）
2. **塊にまとめ、塊ごとに 1 文の説明を書く。** 書けない残りは「まだ分けられて
   いない」として残す。**この時点で行き先の名前が決まる**
3. **塊を 1 つ選ぶ。まだ動かさない。** その塊がテストで保護されているかを
   確かめる（ステップ A。保護が無ければそれが先）
4. **新しいファイルを作り、塊を切り取って貼る。中身は 1 行も変えない。**
   移動前と移動後で本体の字面が一致することを確かめられる形にしておく
5. **公開範囲を決める。** 塊の外から呼ばれていないものは、新しいファイルの
   中で非公開にする。**ここが分割の実質的な成果**（`lang/` の該当パックの
   「この言語での『完了』の形」を読む）
6. **ビルド定義とテストを更新する。** 新しいファイルの登録漏れは典型的な事故
   （`SKILL.md`「テストがグリーンでも、動くとは限らない」）
7. **元のファイルの残りを見なおす。** 減った結果、残りが 1 文で言えるように
   なっていたら、**そのときに元のファイルを改名する**

**1 コミット 1 塊。** 塊が大きければ関数 1 つずつでもよい。移動の途中で
グリーンが崩れる状態を作らない。

**移動は安全だがゼロコストではない。** 同じファイルにあったから見えていた
非公開の定義（ファイル内関数、内部マクロ、ファイル内の状態）が、移すと見えなく
なる。**移した先で「足りない」と言われたものの一覧が、そのまま「その塊が本当は
何に依存していたか」だ。** 予想より多ければ切り目が悪い。戻して切り直す。
ここでも、依存を推測せずツールに教えてもらうのが速い。

**番号付きの受け皿を新しく作らない。** 溢れたものを `misc4` に移すのは、何も
約束しない場所を増やすだけで、翌週には同じ状態になる。**行き先は必ず「何のため
か」を言える名前にする。**

**元のファイルが無くなることを終点にする。** 名前が何も約束しないファイルが
残っているかぎり、次の人はそこに置く。半分だけ分割した状態は「どちらに何が
あるか分からない」ぶん、着手前より悪いこともある。**一度に全部やる必要はないが、
どこで終わるかは最初に決める。**

**すでに行き先が存在していないか先に確かめる。** 過去に切りだされた小さな
モジュールが、対応する処理を雑多なファイルに残したままになっていることがある
（`abilities` があるのに能力値計算が `misc` にある）。この場合は新設ではなく
**既存モジュールへの合流**で、新しい名前を考える必要がない。最も安い分割だ。

### クラス抽出

「1. 重複コード」の「クラス抽出」と同じ手順。責務の一方を新クラスに移す。

### サブクラス抽出

一部のインスタンスだけが使うフィールド・メソッドがある場合（`if (type == A) ... else ...` が散在している）。

1. サブクラスを作る（中身は空）。インスタンス生成箇所をファクトリー経由にする
2. 型に依存する分岐を 1 つずつ、サブクラスのメソッドのオーバーライドに置きかえる
3. 分岐がなくなったら、親クラスの該当メソッドを抽象メソッドにする

### インターフェース抽出

クラスの利用者が使っている部分だけを切りだす。利用者ごとに必要なメソッドが違うなら、インターフェースを複数に分けてよい。

1. 利用者が実際に呼んでいるメソッドを列挙する（grep で確認）
2. それらだけを持つインターフェースを定義し、既存クラスに実装させる
3. 利用者側の型宣言を、具象クラスからインターフェースに変える（1 箇所ずつ）

## 4. 不適切な責務配置

### メソッド移動（Move Method）

あるメソッドが、自分のクラスのフィールドよりも他クラスのフィールドを多く使っているなら、そのメソッドは他クラスに属すべきだ。

1. 移動先クラスに、同じ処理のメソッドを作る（元のクラスからのコピー）
2. 元のメソッドを、移動先への委譲に置きかえる。テストで確認
3. 呼びだし箇所を 1 つずつ、移動先を直接呼ぶように変える
4. 元のメソッド（空の委譲）を削除する

### フィールド移動（Move Field）

あるフィールドが、自分のクラスよりも他クラスのメソッドから多く使われているなら、移す。

1. 移動先にフィールドを追加する。元のフィールドの読み書きを、移動先へのアクセサー経由にする
2. 元のフィールドを削除する
3. 利用箇所を 1 つずつ、移動先を直接使うように変える

### ファサード導入

利用者が複数のクラスの複雑な組みあわせを毎回書いている場合。

1. その組みあわせをひとまとめにする関数（またはクラス）を作る
2. 利用箇所を 1 つずつファサード経由に置きかえる
3. ファサードだけが使うようになったクラスを、公開範囲から外す（可視性を絞る）

## 5. 名前が意図を表さない

**この分類は最も安全で効果が高い。** 自動リネームが使えるなら、テスト保護なしでも実行できる。着手コストが低く、以後の全作業（コードを読む作業すべて）を楽にするので、他の項目より先にまとめて片づける価値がある。

### 名前の変更

1. IDE の自動リネームを使う。使えない場合は、宣言と全参照箇所を grep で洗いだしてから一括で変える
2. テストを実行して確認する

**良い名前の条件。** 「何をするか」ではなく「何であるか／何を返すか」を語る。`getData` より `parseHeader`。`flag` より `isExpired`。`process` は何も語っていない。`tmp`, `data`, `info`, `manager`, `helper`, `util` は、ほぼ常に改名の余地がある。

**名前が書けないときは、設計の問題。** 「これを一言で言えない」なら、その関数は複数のことをしている。分割が先だ。

### マジックナンバーの定数化

1. リテラルに名前をつけた定数を定義する
2. リテラルの出現箇所を 1 つずつ定数に置きかえる（**同じ値でも意味が違うなら別の定数にする**）

同じ `0` が「配列の先頭」と「成功のエラーコード」の両方に使われていることがある。機械的な一括置換は間違いを生む。

## 6. 複雑な条件分岐

### ガード節導入（Introduce Guard Clause）

ネストを浅くする。**最も費用対効果が高い手法で、ここから始める。**

1. 最も外側の `if` を反転させ、条件を満たさない場合に早期リターン（または例外）する形にする
2. 残った本体のインデントを 1 段下げる。テストで確認
3. 内側のネストについて繰り返す

```
// 前
if (a != null) { if (b > 0) { ... } }
// 後
if (a == null) return default;
if (b <= 0) return default;
...
```

**「異常系を先に弾き、正常系を平坦に書く」**という形に寄せる。読み手が正常系を追うときに条件を頭に積まなくて済む。

### ガード節にしてよい分岐、してはいけない分岐

ガード節が効くのは**捨てる側がある**分岐だけだ。「条件を満たさないから、ここで終わる」という形に意味がある場合。

**どちらの枝も正常な値を返す分岐は、ガード節にしない。** 対称に書く。片方だけを早期リターンにすると、そちらが「例外的」に見えてしまう。`if/else` で対等に並べるか、条件式そのものを値として書く。

**理由。** 早期リターンは「ここで打ち切る」という非対称な意図を持つ記法だ。両方の枝が対等な選択肢なら、非対称に書くと読み手が「なぜ片方だけ先に返すのか」を探してしまう。関数型言語のように **`if` が値を持つ式**だと考えて、選択肢を並べる形に寄せる。

判断の目安。

| 分岐の性質 | 書き方 |
|---|---|
| 片方が「異常・打ち切り」（null チェック、範囲外、エラー） | **ガード節**（早期リターン） |
| 両方が正常な結果（値の選択、場合分けの計算） | **`if/else` または三項演算子** |
| 枝が 3 つ以上で、どれも正常 | `switch`、ディスパッチテーブル、`else if` の連鎖 |

**真偽を表す型がない言語では、条件式をそのまま返さない。** 戻り値が「真偽」か「個数」かを読み手が判断できず、真のときに何が返るかが言語規格の知識に依存する。詳細は `lang/c.md`「真偽を値として返すときは明示する」。

### 条件分岐のポリモーフィズム化

同じ条件による分岐が複数の関数に散らばっている場合（片方だけ直す事故が起きる典型）。

1. 分岐の各枝に対応するクラスを作り、共通のインターフェースを持たせる
2. 分岐のひとつを、対応するクラスのメソッド呼びだしに置きかえる。テストで確認
3. 残りの分岐を 1 つずつ置きかえる
4. すべて置きかえたら、条件判定を「どのクラスを選ぶか」の 1 箇所（ファクトリー）に集約する

**分岐が 1 箇所にしかないなら、この手法は使わない。** クラスが増えるだけで読みにくくなる。散在していることが適用の条件だ。

### スイッチ文の置き換え

値による多分岐は、テーブル（辞書・マップ）で置きかえられる。

1. 分岐の対応関係を表す辞書（キー → 値、またはキー → 関数）を定義する
2. `switch` / `if-elif` 連鎖を、辞書の参照に置きかえる
3. **既定値（該当キーがない場合）の扱いを、元の `default` 節と同じにする**

3 番を外すと、未知の値に対するふるまいが静かに変わる。元が例外を投げていたのか、無視していたのかを必ず確認する。

## 7. 強すぎる依存関係

**この分類はコストが高い。** 手をつける前に、その依存が実際に問題を起こしているか（変更のたびに複数箇所を直しているか）を確認する。「依存が多い」だけでは動機が弱い。

### 依存逆転（Dependency Inversion）

具体（下位モジュール）への依存を、抽象（インターフェース）への依存に変える。手順は `dependency-breaking.md` の「インターフェースによる置きかえ」と同じ。

要点は **インターフェースを「利用者側」に置く**こと。利用者が必要とする形で定義し、実装側がそれに合わせる。実装側の都合で定義すると、抽象化した意味がない。

### インターフェース導入

「3. 肥大化クラス／モジュール」の「インターフェース抽出」と同じ手順。

### モジュール分割（依存の向きを直す）

**「3. 肥大化クラス／モジュール」の「モジュール分割と再命名」とは目的が違う。**
あちらは責務が混ざったファイルを分けること、こちらは**モジュール間の依存の向き**
を直すこと。同じファイルに両方の問題があることは多いが、責務で分けるのが先だ
（依存の絵は、責務が混ざったままでは読めない）。

1. 依存の向きを図にする（どのファイルがどれを import しているか）。循環があればそれが最優先の問題
2. 循環を切る。片方向にするために、共通部分を第三のモジュールに切りだすか、インターフェースを一方に置く
3. 結合の強い塊を、1 つのモジュール（ディレクトリ、パッケージ）にまとめる
4. モジュール外に公開する要素を絞る（可視性を狭める、`__all__` を定義する、内部用ヘッダーを分ける）

4 番が実質的な成果だ。公開範囲を絞ることで、以後の変更が波及しなくなる。

## 8. データの散在

複数のクラスが同じフィールドの組（`x, y` / `startDate, endDate` / `host, port, timeout`）を別々に持っている場合。

1. その組を表す型（構造体、データクラス、値オブジェクト）を定義する
2. 1 つのクラスのフィールド群を、新しい型のフィールド 1 つに置きかえる。アクセサーは残して呼びだし側を壊さない。テストで確認
3. 残りのクラスについて 1 つずつ繰り返す
4. 新しい型に、そのデータに関する処理（検証、変換、比較）を集める

**4 番を省略すると、ただのデータ入れ物が増えるだけ。** 散在していたデータを 1 箇所に集める価値は、そのデータを扱うロジックも一緒に集まることにある。

### 窓口モジュールに寄せる（1 つのデータが多数の場所から直接触られている場合）

グローバル変数、シングルトン、公開された可変状態。**フィールドの組ではなく、
1 つのデータが多数のファイルから直に読み書きされている**形。散在しているのは
データの定義ではなく**それに触る権利**なので、上の手順とは進め方が違う。

まず**棚おろしをする**。対象ごとに「参照数・書きこみ数・別名（ポインタや参照を
とっている箇所）・触っているファイル数」を数え、**区分に分けて**表にする。
一度に全部は動かせないので、区分が着手の単位になる。数えかたは機械化して
おく（スクリプト 1 本）。**同じ数えかたを終わりにもう一度使えることが要点で、
「12 箇所が触っていたものが窓口 1 つになった」が成果の記述になる。**

区分ごとに次を踏む。

1. **その区分に「導出」があるかを見る。** 参照箇所が同じ計算を繰りかえして
   いるなら（範囲の切りつめ、添字の折りかえし、上限との比較）、それが隠す
   べき中身だ。計算が無く純粋な置き場なら、隠すのは配置だけになる
2. **導出がある場合：まず変更前の計算をテストに写しとって固定する**
   （`refactoring-loop.md`「変更前のロジックをテストに写す」）。この時点で
   本体は呼びかえない。**ふるまいが変わらないコミットになる**
3. **新しいモジュールを作り、データをその中に閉じる。** 窓口（アクセサ）だけを
   公開する
4. **呼びだし側を窓口経由に書きかえる。** ファイル単位、または役割単位で
   1 コミット。**ここで「同じ計算をしている箇所」が窓口 1 つに畳まれる**
5. **直接触れないようにする。** 言語機能で外から見えなくし、共有の宣言から
   消す（`lang/` の該当パックの「この言語での『完了』の形」を読む）

**新しいモジュールに依存を持ちこまない。** 全域ヘッダや共通の取りこみを
入れないでおくと、テストがそのモジュール 1 つだけを対象に動かせる。移せない
副作用は呼びだし側に残す。ここを妥協すると、テストのために依存が芋づるで
必要になり、次の区分の着手コストが上がる。

**置き場だけの区分でも、テストを書く価値はある。** 隠す計算が無くても
「同じ添字はいつでも同じ実体を指す」「実体どうしが重なっていない」「書いた
ものが残る」は、変更前は「配列だから当然」で済んでいたことが、窓口越しに
なると当然ではなくなる（写しを返す実装ならそこで落ちる）。

**5 番まで進めない状態で項目を閉じない。** 窓口を作ったが直接参照も残って
いる状態は、新旧 2 つの経路が併存する分だけ悪化している。

### データのカプセル化

公開フィールドを直接読み書きされている場合。

1. アクセサー（getter/setter、プロパティ）を追加する
2. 直接アクセスを 1 箇所ずつアクセサー経由に置きかえる
3. フィールドを非公開にする
4. setter が不要なフィールドは setter を削除する（不変にする）

4 番まで進めると、状態が変わる箇所が減って追跡が楽になる。

## 9. 不要なコード

**削除は最も安全で、コンテキストを軽くする効果がある。** 早めに片づけると以後の調査が速くなる。

### デッドコード削除

1. **参照を裏取りする。** 名前を全文 grep する。動的呼びだし（リフレクション、`getattr`、関数名の文字列）、設定ファイル経由の参照、外部公開 API、ビルド対象外ファイルからの参照を確認する
2. **git 履歴で導入意図を確認する。** 下記「未使用でも消してはいけないもの」を読む
3. 1 と 2 の両方を通ったら削除する
4. テストを実行する。削除したものがテストからだけ使われていたなら、そのテストも一緒に消す

### 未使用でも消してはいけないもの

**参照ゼロは「不要」の証明にならない。** 未使用のコードには、少なくとも 3 つの異なる意味がありうる。

| 種類 | 見分け方 | 扱い |
|---|---|---|
| **本当の残骸** | 導入が古く、以後触られていない。関連する機能が既に別の形で実現済み | 削除する |
| **先行して用意された基盤** | 導入が新しい。または直近も変更されている。コミットメッセージに `foundation`, `scaffold`, `prepare`, `groundwork`, 「基盤」「準備」などの語がある | **消さない。**棚上げにして理由を記録する |
| **外部に利用者がいる API** | 公開ヘッダ・公開パッケージに属する。ライブラリとして配布されている | **消さない。**利用者はこのリポジトリの外にいる |

だから **step 2 が必要**。次の 2 つを実行する。

```
git log --oneline --follow -- <対象ファイル>      # ファイルの導入と変更の履歴
git log --oneline -S '<関数名>' -- <対象ファイル>  # その識別子が現れたコミット
```

導入コミットのメッセージを読む。「〜の基盤を追加」「Model-View 分離の準備」のように、**これから接続する意図が書かれていたら、それは残骸ではなく足場**だ。参照がないのは未完成だからで、消すと進行中の作業を壊す。

**直近も変更されているのに参照ゼロ**という組みあわせは、とくに強い警告だ。誰かが手を入れ続けているものを、外部から「使われていないから」と消してはいけない。

判断がつかないときは削除せず、**ユーザーに確認する**。「参照ゼロだが導入意図が基盤の追加に見える。使う予定があるか」と聞けば数秒で解決する。消してから気づくのとは比較にならない。

**判断を差し戻すことは失敗ではない。** 検出フェーズが「デッドコード」と分類したものを、履歴を読んで「基盤」と再分類するのは、裏取りが機能したということだ。台帳の分類を書きかえて棚上げに移し、理由を記録する。

### 変数インライン化

1 度しか使われず、名前が値の説明になっていない変数（`var tmp = f(x); return tmp;`）。使用箇所に展開して削除する。

**逆はやりすぎない。** 複雑な式に名前をつけた変数は、名前が説明として機能しているので残す。

### メソッドインライン化

「2. 長すぎるメソッド」の「メソッドインライン化」と同じ。

## 10. 理解しづらいロジック

### メソッド抽出で意図を名前にする

**コメントを足して済ませない。** コメントが必要なのは、コードが意図を語っていないから。

1. コメントが説明している範囲を関数として抽出する
2. コメントの内容を関数名にする
3. コメントを削除する

これで、コメントとコードがずれる問題（コードだけ直してコメントが古くなる）が原理的に起きなくなる。

**残すべきコメントもある。** 「なぜこうしたか」（過去の障害、外部仕様の制約、意図的な非効率）はコードに書けない。これは残す。消すのは「何をしているか」を説明しているコメントだけだ。

### アルゴリズム置換（Replace Algorithm）

処理の意図はわかるが、実現方法が回りくどい場合。

1. **先にテストを厚くする。** 置きかえは他の手法より変更範囲が大きいので、代表値とエッジケース（空、1 要素、境界、最大）を追加してから着手する
2. 新しい実装を別の関数として書く
3. 元の関数を、新しい関数への委譲に置きかえる。テストで確認
4. 元の関数を削除し、呼びだし側を新しい関数に向ける

**性能を理由に置きかえるなら、先に計測する。** 「速くなるはず」で書きかえた結果遅くなることは珍しくない。計測なしの性能目的の置換はやらない。
